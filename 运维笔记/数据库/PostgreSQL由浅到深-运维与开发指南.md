# PostgreSQL 由浅到深：运维与开发指南

## 1. 文档概述

- **解决什么问题**：系统梳理 PostgreSQL（简称 PG / pgsql）从入门到进阶的知识体系，覆盖开发侧的 SQL/建模/索引/事务/高级特性，以及运维侧的部署/复制/备份/监控/扩展两条主线。
- **适合哪些读者**：
  - 后端/全栈开发者（需要正确建模、写高效 SQL、用好转义）
  - 运维/SRE/DBA（需要保障可用性、备份可恢复与容量性能）
  - 从 MySQL/MongoDB 转来、希望建立 PG 完整认知的工程师
- **阅读后能获得什么**：建立正确心智模型，掌握分阶段学习路径，能完成本地「用户-订单」练习与基础主从/备份演练，并知道生产环境关键检查项。

> 核心结论：PostgreSQL 难的不是「会写 SELECT」，而是**规范化与约束设计**、**索引与执行计划**、**事务隔离与锁**，以及生产上的**流复制 + 基备/WAL 归档 + 监控 vacuum**。先把单机 SQL 与 `EXPLAIN` 学透，再上高可用；水平分片通常最后考虑。

## 3. 核心概念

### 3.1 PostgreSQL 是什么

PostgreSQL 是**开源对象-关系型数据库**（ORDBMS）：以表（关系）存储数据，同时支持丰富类型、扩展、JSON、全文检索等「对象」能力。强调 **SQL 标准符合度、数据完整性、可扩展性**。

| 概念 | 含义 |
|------|------|
| Database | 逻辑库，一个实例可有多个库 |
| Schema | 库内命名空间（默认 `public`） |
| Table | 表 |
| Row / Column | 行 / 列 |
| Index | 索引 |
| View / Materialized View | 视图 / 物化视图 |
| Extension | 扩展（如 `pg_stat_statements`、`postgis`） |

层级关系：

```text
Instance (Cluster) → Database → Schema → Table → Row / Column
```

> 术语注意：PG 口语里的 **cluster** 常指「一次 `initdb` 得到的数据目录/实例」，不等于 MongoDB 的分片集群。

### 3.2 适合与不适合

**较适合**：

- 强一致、复杂查询、多表关联的业务系统
- 需要约束完整（主键/外键/唯一/检查约束）的领域模型
- JSON/JSONB 半结构化与关系数据并存
- 分析与 OLTP 兼顾（适度；超大规模分析可配合专用引擎）
- 地理、全文、向量等扩展场景（PostGIS、pgvector 等）

**不太适合 / 需谨慎**：

- 极致写吞吐且可接受弱模型的日志海量写入（可评估专用时序/日志方案）
- 简单 KV 且无事务需求时可能过重
- 水平扩展成本高于「垂直扩展 + 读写分离」时，不要过早分片

### 3.3 开发与运维各自关心什么

| 维度 | 开发关注 | 运维关注 |
|------|----------|----------|
| 数据 | 表设计、约束、迁移 | 数据目录、表空间、磁盘 |
| 性能 | SQL、索引、`EXPLAIN` | `shared_buffers`、I/O、连接数、autovacuum |
| 可用 | 超时、重试、连接池 | 流复制、故障切换、备份 |
| 扩展 | 分区表、读写分离友好查询 | 逻辑复制、Citus/分片、只读副本 |
| 安全 | 最小权限、SQL 注入防护 | 认证、`pg_hba.conf`、TLS、审计 |

### 3.4 关键内部机制（先建立直觉）

1. **MVCC（多版本并发控制）**：读写尽量不互堵；更新/删除会产生旧版本行，需要 **VACUUM** 回收。
2. **WAL（Write-Ahead Logging）**：先写日志再落数据页，是崩溃恢复与复制的基础。
3. **进程模型**：一个客户端连接通常对应一个 backend 进程；连接数不能无限涨 → 生产常用 **连接池**（PgBouncer 等）。
4. **统计信息**：优化器依赖 `ANALYZE` 统计；统计过期会导致烂计划。

## 4. 开发视角：由浅到深

### 4.1 L1：SQL 与 CRUD

**要做什么**：掌握建表、增删改查、过滤排序分页。  
**为什么**：所有业务数据访问的基础。  
**预期结果**：能用 `psql` 完成基本操作。

```sql
-- 建表
CREATE TABLE users (
  id         BIGSERIAL PRIMARY KEY,
  email      TEXT NOT NULL UNIQUE,
  name       TEXT NOT NULL,
  level      TEXT NOT NULL DEFAULT 'normal',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 插入
INSERT INTO users (email, name, level)
VALUES ('alice@example.com', 'Alice', 'vip')
RETURNING id;

-- 查询
SELECT id, email, name
FROM users
WHERE level = 'vip'
ORDER BY created_at DESC
LIMIT 20;

-- 更新 / 删除
UPDATE users SET name = 'Alice Wang' WHERE id = 1;
DELETE FROM users WHERE id = 2;
```

常用要点：

- 优先用 **`TIMESTAMPTZ`**（带时区）而不是无时区 `TIMESTAMP`
- 主键常用 `BIGSERIAL` / `GENERATED BY DEFAULT AS IDENTITY` / UUID（按业务选）
- 分页：浅分页可用 `LIMIT/OFFSET`；深分页改用键集分页（`WHERE id > ? ORDER BY id LIMIT n`）

### 4.2 L2：数据建模与约束（关系库分水岭）

**要做什么**：用主键、外键、唯一、检查约束表达业务不变量。  
**为什么**：约束在数据库层兜底，比只靠应用校验更安全。  
**预期结果**：能设计规范的用户-订单模型，并理解何时适度反范式。

```sql
CREATE TABLE orders (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id),
  amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
  status      TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'cancelled')),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
```

建模原则：

1. **先规范化**（减少冗余与更新异常），再按读路径做**有依据的反范式**。
2. 外键要开，除非有明确的分库/性能豁免理由。
3. 状态字段用约束或枚举（`CREATE TYPE ... AS ENUM`）限制合法值。
4. 金额用整数分（`INTEGER`/`BIGINT`）或 `NUMERIC`，避免 `float`。
5. 软删除、审计字段提前设计，避免后期大改。

与 MongoDB 对照直觉：

- PG：表结构 + 约束优先；JSON 作补充  
- Mongo：文档结构灵活；约束靠应用/校验器

### 4.3 L3：索引与执行计划

**要做什么**：为高频过滤/排序/关联建索引，并用 `EXPLAIN (ANALYZE, BUFFERS)` 验证。  
**为什么**：错误计划或无索引会让延迟随数据量线性恶化。  
**预期结果**：关键 SQL 走 Index Scan / Index Only Scan，行数估计大致合理。

常见索引类型：

| 类型 | 典型用途 |
|------|----------|
| B-Tree（默认） | `=`、`<>`、范围、排序 |
| Hash | 等值（场景较窄） |
| GIN | JSONB、数组、全文 |
| GiST / SP-GiST | 地理、范围等 |
| BRIN | 超大表、与物理顺序相关的列（如时间追加） |

```sql
-- 复合索引：等值列靠前，范围/排序列靠后（经验）
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);

-- JSONB
CREATE INDEX idx_users_profile_gin ON users USING GIN (profile jsonb_path_ops);

-- 查看计划（必须会）
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

看计划时关注：

- `Seq Scan` 是否合理（小表可以，大表过滤通常不该）
- 实际行数 vs 估计行数是否偏差巨大（统计过期 → `ANALYZE`）
- 是否有意外的嵌套循环爆炸、错误的 Hash/Merge Join
- `Buffers`：读了多少页（shared hit/read）

### 4.4 L4：连接、聚合与窗口函数

**要做什么**：用 JOIN/聚合/窗口完成业务统计，而不是在应用层循环查库。  
**为什么**：正确下推到数据库通常更快、更一致。  
**预期结果**：能写清多表关联与排行/累计类查询。

```sql
-- 用户已支付订单汇总
SELECT u.id, u.name,
       COUNT(o.id) AS paid_cnt,
       COALESCE(SUM(o.amount_cents), 0) AS paid_total
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id AND o.status = 'paid'
GROUP BY u.id, u.name
ORDER BY paid_total DESC;

-- 窗口函数：每个用户最近一笔订单
SELECT *
FROM (
  SELECT o.*,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders o
) t
WHERE rn = 1;
```

### 4.5 L5：事务、隔离级别与锁

**要做什么**：理解事务边界、隔离级别与常见锁等待。  
**为什么**：并发下的丢更新、幻读、死锁都出在这里。  
**预期结果**：能选择合适隔离级别，并写出安全的库存扣减。

```sql
BEGIN;

-- 条件更新（乐观思路）
UPDATE products
SET stock = stock - 1
WHERE id = 100 AND stock >= 1;

-- 检查 FOUND / 返回行数，不足则 ROLLBACK
COMMIT;
```

隔离级别（从弱到强直觉）：

| 级别 | 特点 |
|------|------|
| Read Committed（默认） | 语句级看到已提交数据；实现简单，最常用 |
| Repeatable Read | 事务中快照稳定；可遇序列化失败需重试 |
| Serializable | 最强；冲突时事务失败，应用需重试 |

注意：

- 长事务会妨碍 vacuum、撑大 bloat、拖垮系统——**事务要短**。
- `SELECT ... FOR UPDATE` 用于需要强互斥的行锁场景。
- 死锁：看日志与 `pg_stat_activity` / `pg_locks`，从业务上固定加锁顺序。

### 4.6 L6：高级特性（开发加分项）

按需掌握，不必一次学完：

1. **JSONB**：半结构化字段；配合 GIN 索引与 `@>` / `jsonb_path_query`
2. **CTE（`WITH`）**：可读性强；注意是否物化（版本差异）
3. **分区表（Declarative Partitioning）**：按时间/哈希拆大表
4. **物化视图**：加速报表；需刷新策略
5. **触发器 / 函数（PL/pgSQL）**：封装约束与副作用（慎用过多业务逻辑入库）
6. **LISTEN/NOTIFY**：轻量消息通知
7. **逻辑复制 / publication**：做异构同步、部分表复制
8. **扩展**：`pg_stat_statements`（必装级）、PostGIS、pgvector 等

应用层实践：

- **永远参数化查询**，防 SQL 注入
- 使用连接池；Web 应用不要「每请求新建大量直连」
- 迁移工具：Flyway / Liquibase / golang-migrate / Prisma migrate 等
- 超时：`statement_timeout`、应用侧 query timeout
- 批量写入用 `COPY` 或多值 `INSERT`，避免逐行往返

## 5. 运维视角：由浅到深

### 5.1 L1：安装、目录与基础配置

**要做什么**：会安装、初始化、改关键参数、用 `psql` 观测。  
**为什么**：所有 HA/备份都建立在稳定单机认知上。  
**预期结果**：能启动实例、建库建用户、修改并 reload/restart 配置。

```bash
# 常见路径（发行版不同，【需要确认】）
# 数据目录：/var/lib/postgresql/16/main 或 $PGDATA
# 配置：postgresql.conf / pg_hba.conf

psql -U postgres -c "SELECT version();"
```

必须认识的配置文件：

| 文件 | 作用 |
|------|------|
| `postgresql.conf` | 内存、WAL、日志、并行等参数 |
| `pg_hba.conf` | 客户端认证与访问控制（谁能从哪连、用什么认证） |
| `pg_ident.conf` | 系统用户映射（较少改） |

入门级关键参数（值需按机器测算，勿照抄）：

```ini
# 概念示例 —— 上线前按内存与压测调整
shared_buffers = 4GB          # 常从物理内存 25% 量级起步评估
work_mem = 64MB               # 单排序/哈希操作；连接多时小心乘积
maintenance_work_mem = 1GB
effective_cache_size = 12GB   # 给优化器的「OS 缓存」提示
max_connections = 200         # 宁小勿大，前接连接池
wal_level = replica
listen_addresses = 'localhost'  # 生产改为内网地址
```

观测入口：

```sql
SELECT * FROM pg_stat_activity;
SELECT * FROM pg_stat_database;
SELECT * FROM pg_stat_bgwriter;
```

生产基线：

- 独立数据盘、定期文件系统监控
- 认证不要 `trust` 对公网；生产用 `scram-sha-256`
- 开启必要日志：慢 SQL、连接、错误、锁等待（按噪音权衡）
- 安装 `pg_stat_statements`

### 5.2 L2：流复制与高可用

**要做什么**：搭建 Primary + Standby 物理流复制，理解切换。  
**为什么**：单机宕机不可接受；流复制是 PG 高可用基础。  
**预期结果**：主库写入能在从库看到；主库宕机可提升从库（配合工具更稳）。

核心概念：

- **物理流复制**：从库是字节级副本，适合 HA/只读扩展
- **同步 / 异步**：同步更安全但写延迟更高；异步相反
- **复制槽（replication slot）**：防止所需 WAL 被过早清理（也要防槽卡住撑爆磁盘）
- HA 工具生态：Patroni、Repmgr、pg_auto_failover 等（【需要确认】你们选型）

示意步骤（逻辑）：

1. 主库开 `wal_level=replica`，允许复制用户连接  
2. 用 `pg_basebackup` 拉起从库数据目录  
3. 配置 `primary_conninfo`，启动 standby  
4. 主库查 `pg_stat_replication`，从库查 `pg_is_in_recovery()`

```sql
-- 主库
SELECT pid, application_name, state, sync_state, replay_lag
FROM pg_stat_replication;

-- 从库
SELECT pg_is_in_recovery();
```

读写分离注意：从库有复制延迟；会话级写后读可能读到旧数据。

### 5.3 L3：备份与恢复（可恢复才算数）

**要做什么**：建立「基备 + WAL 归档」或逻辑备份策略，并演练恢复。  
**为什么**：备份文件在不等于能 RPO/RTO 达标。  
**预期结果**：能在演练环境完成一次时间点恢复（PITR）或逻辑恢复。

常见方案：

| 方案 | 说明 | 适用 |
|------|------|------|
| `pg_dump` / `pg_restore` | 逻辑备份 | 中小库、迁移、逻辑级恢复 |
| `pg_basebackup` + WAL 归档 | 物理基备 + PITR | 生产标准能力 |
| Barman / pgBackRest / wal-g | 专业备份套件 | 生产推荐 |
| 快照（LVM/云盘） | 需一致性策略 | 与归档配合评估 |

```bash
# 逻辑备份示例
pg_dump -Fc -d shop -f shop.dump

# 恢复示例
pg_restore -d shop_new --create shop.dump
# 或新建库后：
# createdb shop_new && pg_restore -d shop_new shop.dump
```

PITR 能力依赖：**连续 WAL 归档** + 定期基备。务必定期做恢复演练。

### 5.4 L4：Vacuum、膨胀与维护

**要做什么**：理解 autovacuum，监控死元组与表膨胀。  
**为什么**：MVCC 下不 vacuum，表会膨胀、性能会塌。  
**预期结果**：知道如何观察、何时调参、何时 `VACUUM (FULL)`（慎用）。

```sql
-- 看用户表的 vacuum / analyze 情况（概念查询）
SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum, last_analyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

原则：

- 优先让 **autovacuum** 健康工作，而不是频繁手工 `VACUUM FULL`
- `VACUUM FULL` 会持强锁、重写表，业务高峰禁用
- 长事务、废弃复制槽、挂起的 prepared transaction 都是 vacuum 杀手
- 大批量删除/更新后关注相关表与索引 bloat

### 5.5 L5：监控、性能与容量

必看指标/视图：

- 连接数、活跃会话、等待事件（`pg_stat_activity`）
- 缓存命中率、checkpoint、脏页写回（`pg_stat_bgwriter` 等）
- 磁盘空间、WAL 目录增长、复制延迟
- 慢 SQL / Top SQL（`pg_stat_statements`）
- 锁与阻塞链
- autovacuum 是否跟上

调优方向：

- 内存：`shared_buffers` / `work_mem` / OS page cache 平衡
- I/O：SSD；合理 `checkpoint` 相关参数，避免周期性 penaltyspike
- 连接：应用池 + PgBouncer；降低 `max_connections`
- SQL：先改查询与索引，再改参数
- 大表：分区、归档冷数据

### 5.6 L6：安全、升级与扩展形态

安全：

- `pg_hba.conf` 最小暴露面；禁止公网 `trust`
- 角色最小权限：业务账号不要用超级用户
- TLS；密钥与密码轮换
- 审计：`pgaudit` 等（按合规）
- 防注入主要在应用层参数化；DB 侧限制危险对象权限

升级：

- 小版本：通常可替换二进制滚动
- 大版本：`pg_upgrade` 或逻辑迁移；提前在副本验证
- 扩展版本与主版本兼容性要查清

扩展形态：

- 只读副本（流复制）→ 读写分离  
- 分区表 → 单库内水平管理大表  
- 逻辑复制 → 多活/迁移/部分同步  
- 分布式方案（Citus 等）→ 真分片场景再上

## 6. 完整示例：本地「用户-订单」小练习

### 6.1 建库建表

```sql
CREATE DATABASE shop;
\c shop

CREATE TABLE users (
  id         BIGSERIAL PRIMARY KEY,
  email      TEXT NOT NULL UNIQUE,
  name       TEXT NOT NULL,
  level      TEXT NOT NULL DEFAULT 'normal',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id           BIGSERIAL PRIMARY KEY,
  user_id      BIGINT NOT NULL REFERENCES users(id),
  amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
  status       TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'cancelled')),
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
```

## 7. 常见问题与排查

| 现象 | 可能原因 | 解决方法 |
|------|----------|----------|
| 查询突然变慢 | 缺索引、统计过期、计划退化、膨胀 | `EXPLAIN ANALYZE`；`ANALYZE`；查 bloat；补索引 |
| 连接数打满 | 无连接池、泄漏、`max_connections` 过大导致抖动 | PgBouncer；修泄漏；降直连数 |
| 磁盘暴涨 | WAL 堆积、复制槽落后、bloat、日志过多 | 查 slot/复制；修消费端；vacuum；控日志 |
| 主从延迟高 | 网络/磁盘慢、长事务、大查询打从库 | 升 IOPS；杀长事务；分流只读负载 |
| 锁等待/堆积 | 缺索引更新过宽、长事务、`FOR UPDATE` 滥用 | 查阻塞链；缩短事务；优化 SQL |
| autovacuum 跟不上 | 参数过保守、IO 打满、长事务挡清理 | 调表级 vacuum 参数；清长事务；升 IO |
| 认证失败 | `pg_hba.conf`、密码加密方式、`search_path`/库名错 | 对一下 hba 与连接串；SCRAM 配置 |
| 升级后变慢 | 未 `ANALYZE`、参数未迁移、扩展差异 | 全库分析；对比参数与执行计划 |

阻塞会话排查示意：

```sql
SELECT pid, usename, state, wait_event_type, wait_event, query_start, left(query, 120)
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

## 8. 注意事项与最佳实践

1. **生产要有副本与可演练备份**，单机 + 不定时 dump 不够。  
2. **先 SQL/索引，再参数，最后基础设施扩容**。  
3. **约束留给数据库**：能用外键/唯一/检查表达的，不要只写在代码注释里。  
4. **短事务 + 健康的 autovacuum** 是 PG 长期稳定的根基。  
5. **连接池几乎是 Web 业务标配**；慎抬 `max_connections`。  
6. **`EXPLAIN (ANALYZE, BUFFERS)` 是开发日常工具**，不是出事后才用。  
7. **大表提前想分区与归档**，不要等单表数百 GB 再救火。  
8. **权限最小化**：业务账号、迁移账号、只读账号分离。  

开发与运维交叉必懂：

- MVCC / vacuum / bloat 如何影响性能  
- WAL / 复制 / 备份如何决定 RPO  
- 隔离级别与重试策略  
- 连接池对事务与会话特性（临时表、prepared statement）的影响

## 10. 总结

- PostgreSQL 的核心是 **关系模型 + 强约束 + MVCC/WAL**。  
- 开发侧优先掌握：**SQL/约束 → 索引与执行计划 → 事务与锁 → JSONB/分区等进阶**。  
- 运维侧优先掌握：**配置与认证 → 流复制 → 备份 PITR → vacuum/监控 → 连接池与安全**；分片最后上。  
- 两边交汇点是：**执行计划、膨胀与 vacuum、复制延迟、连接数、可恢复性**。
