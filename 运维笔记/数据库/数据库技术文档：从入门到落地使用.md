## 1. 文档概述

### 1.1 解决什么问题

本文档系统说明 **PostgreSQL**（常简称 **pg** 或 **Postgres**）是什么、如何安装、如何连接，以及如何用 SQL 完成建库、建表、增删改查、索引、事务与日常运维。目标是让你从「听说过」走到「能在本机/服务器上真正用起来」。

### 1.2 适合哪些读者

- 刚接触关系型数据库的开发者
- 从 MySQL 等库迁移、需要快速上手 Postgres 的工程师
- 需要做基础备份、配置与排错的运维/全栈开发者

### 1.3 阅读后能获得什么

- 理解 Postgres 的定位、核心特性，以及与 MySQL 等的大致差异
- 能在 macOS / Linux（含 Docker）完成安装并连上数据库
- 掌握 Schema、角色、权限等基础对象模型
- 能独立完成 CRUD、JOIN、索引、事务等日常开发操作
- 了解备份恢复、日志、配置要点及视图/JSON/扩展等进阶能力
- 手边有一份可复制的命令与 SQL 速查表

### 1.4 先讲结论（核心思路）

Postgres 是一款**开源、对象-关系型（ORDBMS）、强事务（ACID）**的数据库。日常使用路径很清晰：

1. **安装服务** → 启动 `postgres` 进程  
2. **用角色登录** → `psql` 或应用连接串  
3. **建库 / 建 Schema / 建表** → 写入结构化数据  
4. **用 SQL 查询与事务** → 保证一致性  
5. **用索引与运维工具** → 保证性能与可恢复性  

默认端口是 **5432**；默认超级用户在很多安装方式下叫 **`postgres`**。下文示例以 PostgreSQL **16** 为主（多数语法在 14–17 通用；个别版本差异处会标注 **【需要确认】**）。

## 3. 核心概念

### 3.1 PostgreSQL 是什么

**PostgreSQL** 是一款开源的对象-关系型数据库管理系统（Object-Relational Database Management System）。它用标准 SQL 管理结构化数据，同时支持丰富的数据类型、扩展机制与高级查询能力。

一句话定位：**适合需要强一致性、复杂查询、可扩展类型与长期可维护性的业务系统。**

### 3.2 核心特性（结论优先）

| 特性 | 含义（白话） | 为什么重要 |
|------|-------------|-----------|
| **开源** | 开源许可（PostgreSQL License），可自由使用与修改 | 无授权费用门槛，生态开放 |
| **关系型** | 数据以表、行、列组织，用 SQL 操作 | 结构清晰，约束与关联表达力强 |
| **ACID** | 原子性、一致性、隔离性、持久性 | 转账、订单等场景可依赖事务保证 |
| **MVCC** | 多版本并发控制：读写尽量不互相阻塞 | 高并发下读性能与一致性兼顾 |
| **扩展性** | 可通过 Extension 增加类型、函数、索引等 | 同一引擎可覆盖 GIS、全文检索等 |
| **标准兼容** | 对 SQL 标准支持较完整 | 复杂查询、窗口函数、CTE 等能力强 |
| **JSON/JSONB** | 原生支持半结构化文档 | 关系模型 + 文档灵活字段可并存 |

### 3.3 与其他数据库的简要对比

点到为止，便于选型时心里有数：

| 维度 | PostgreSQL | MySQL（常见 InnoDB） | 备注 |
|------|------------|----------------------|------|
| 定位 | 功能全面的通用 ORDBMS | 广泛用于 Web / OLTP | 两者都能支撑大量业务 |
| 复杂查询 / 标准 SQL | 通常更强、更完整 | 够用，部分高级特性较晚或有差异 | 分析型 SQL、CTE、窗口函数等 Postgres 很常见 |
| JSON | JSONB + 索引（GIN 等）成熟 | JSON 支持可用 | 文档型字段多时可优先考虑 Postgres |
| 扩展生态 | PostGIS 等扩展极强 | 插件/引擎模式不同 | GIS、向量等场景常选 Postgres |
| 运维习惯 | `pg_dump`、复制、WAL | `mysqldump`、复制等 | 工具链不同，概念可类比 |
| 默认隔离级别 | 通常为 **Read Committed** | InnoDB 也多为 Read Committed | 具体以实例配置为准 |

选型建议：

- 需要复杂约束、分析查询、JSONB、GIS、强扩展 → **优先 Postgres**
- 团队已有成熟 MySQL 运维体系、业务简单 CRUD → MySQL 仍然很合适
- 不要用「谁更好」一刀切；用负载、技能栈与生态决定

### 3.4 对象模型：数据库、Schema、表、角色

理解下面这张「层级图」能少踩很多坑：

```text
PostgreSQL 集群（Cluster / Instance）
├── 角色 Role（用户/组，可登录或不可登录）
├── 数据库 Database A
│   ├── Schema public（默认）
│   │   ├── 表 / 视图 / 函数 / 索引 ...
│   │   └── ...
│   └── Schema app
│       └── ...
└── 数据库 Database B
    └── ...
```

关键术语（首次解释）：

- **集群（Cluster）**：同一套数据目录下运行的一整套 Postgres 实例（不是「多台机器组成的集群」那个意思，虽然口语里容易混）。
- **数据库（Database）**：逻辑隔离的命名空间容器；连接时必须指定要连哪个库。
- **Schema（模式）**：库内的命名空间，用来组织表/视图/函数，避免名字冲突。默认常用 `public`。
- **表（Table）**：存放行数据的关系。
- **角色（Role）**：权限主体。Postgres 把「用户」和「组」统一成 Role；能登录的 Role 常被叫作用户。
- **权限（Privilege）**：对库、Schema、表、列、函数等对象的 `SELECT`/`INSERT`/`UPDATE`/`DELETE`/`USAGE` 等授权。

记忆口诀：**先连上实例 → 选中数据库 → 在 Schema 里找表 → 用角色的权限决定能不能读写。**

### 3.5 连接相关概念

- **`psql`**：官方命令行客户端，学习与运维最常用。
- **连接串（Connection URI / DSN）**：应用里一行写清主机、端口、库名、用户、密码等。  
  例：`postgresql://user:password@localhost:5432/mydb`
- **`pg_hba.conf`**：主机认证配置——决定「谁、从哪、用什么方式」可以登录。
- **`postgresql.conf`**：主配置文件——内存、日志、连接数等。

## 4. 实现步骤：安装、连接与基础操作

按顺序完成下列步骤。每一步都写清：**做什么 / 为什么 / 预期结果**。

### 步骤 1：安装 PostgreSQL

#### 方式 A：macOS（Homebrew）

**做什么**

```bash
# 安装（版本号可按需调整）
brew install postgresql@16

# 启动服务（开机自启可选）
brew services start postgresql@16

# 把客户端加入 PATH（按 brew 提示操作；以下为常见写法）
echo 'export PATH="$(brew --prefix postgresql@16)/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

# 验证
psql --version
```

**为什么**：Homebrew 是 macOS 上最常见的本机安装方式，便于开发调试。  
**预期结果**：`psql --version` 输出版本号；服务处于 running 状态。

> 部分环境下首次安装后，本机用户会自动拥有可登录角色，可直接 `psql postgres`。若失败，见第 8 章。

#### 方式 B：Linux（以 Ubuntu/Debian 为例）

**做什么**

```bash
# 更新索引并安装（仓库版本随发行版而变，【需要确认】具体大版本）
sudo apt update
sudo apt install -y postgresql postgresql-contrib

# 服务状态
sudo systemctl status postgresql

# 切换到 postgres 系统用户后进入 psql
sudo -u postgres psql
```

**为什么**：发行版包管理器安装简单，且通常已配置好 systemd 服务。  
**预期结果**：服务 active；能进入 `psql` 提示符 `postgres=#`。

#### 方式 C：Docker（推荐做隔离实验环境）

**做什么**

```bash
docker run -d \
  --name pg16 \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_USER=app \
  -e POSTGRES_DB=appdb \
  -p 5432:5432 \
  -v pg16_data:/var/lib/postgresql/data \
  postgres:16

# 进入容器内的 psql
docker exec -it pg16 psql -U app -d appdb
```

**为什么**：不污染宿主机；版本可一键切换；适合教程与 CI。  
**预期结果**：容器 Running；能进入 `appdb` 并执行 SQL。

> 生产环境的 Docker/K8s 部署还需考虑存储持久化、资源限制、备份与监控，本文仅覆盖入门用法。

### 步骤 2：用 `psql` 连接

**做什么**

```bash
# 常见连接形式
psql -h localhost -p 5432 -U app -d appdb

# 或使用连接 URI
psql "postgresql://app:secret@localhost:5432/appdb"
```

进入后可试：

```sql
SELECT version();
\conninfo
\l          -- 列出数据库
\q          -- 退出
```

**为什么**：确认客户端、网络、认证都通了，再去做建库建表。  
**预期结果**：能看到版本信息；`\l` 列出数据库。

#### 常用客户端（GUI）

| 客户端 | 说明 |
|--------|------|
| **psql** | 官方 CLI，脚本与运维首选 |
| **pgAdmin** | 官方系 GUI，功能全 |
| **DBeaver** | 通用数据库工具，跨库方便 |
| **TablePlus / DataGrip** | 开发体验较好的商业/付费工具 |

GUI 里一般填：Host、Port、Database、User、Password（SSL 按环境勾选）。

### 步骤 3：理解并创建角色 / 数据库 / Schema

**做什么**

```sql
-- 通常用超级用户执行（示意）
CREATE ROLE app_user WITH LOGIN PASSWORD 'change_me';

CREATE DATABASE shop OWNER app_user;

-- 连接到 shop 后再建 Schema
\c shop

CREATE SCHEMA IF NOT EXISTS sales AUTHORIZATION app_user;

-- 授权示例：允许使用 schema 并操作其中对象
GRANT USAGE ON SCHEMA sales TO app_user;
GRANT CREATE ON SCHEMA sales TO app_user;
```

**为什么**：最小权限原则——应用账号不应长期用超级用户；Schema 便于模块化（如 `sales`、`inventory`）。  
**预期结果**：`\du` 能看到角色；`\l` 能看到 `shop`；`\dn` 能看到 `sales`。

### 步骤 4：建表、约束与索引（DDL）

**做什么**

```sql
SET search_path TO sales, public;

CREATE TABLE customers (
  id            BIGSERIAL PRIMARY KEY,           -- 自增主键
  email         TEXT NOT NULL UNIQUE,
  full_name     TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id            BIGSERIAL PRIMARY KEY,
  customer_id   BIGINT NOT NULL REFERENCES customers(id),
  status        TEXT NOT NULL DEFAULT 'pending',
  amount_cents  INTEGER NOT NULL CHECK (amount_cents >= 0),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 为常用查询条件建索引
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
```

**为什么**：主键保证行唯一；外键保证引用完整；`CHECK` 挡住非法金额；索引加速过滤与排序。  
**预期结果**：`\dt sales.*` 能看到两张表；`\d sales.orders` 能看到约束与索引。

### 步骤 5：CRUD（增删改查）

**做什么**

```sql
-- Create
INSERT INTO customers (email, full_name)
VALUES ('alice@example.com', 'Alice')
RETURNING id, email;

-- Read
SELECT id, email, full_name
FROM customers
WHERE email = 'alice@example.com';

-- Update
UPDATE customers
SET full_name = 'Alice Zhang'
WHERE email = 'alice@example.com'
RETURNING *;

-- Delete（谨慎）
DELETE FROM orders WHERE status = 'cancelled' AND created_at < now() - interval '1 year';
```

**为什么**：四类操作覆盖日常业务写入与读取；`RETURNING` 可立刻拿到写入结果，减少二次查询。  
**预期结果**：插入返回新 `id`；查询能命中；更新后姓名变化。

### 步骤 6：JOIN 与聚合

**做什么**

```sql
-- 内连接：只要有订单的客户
SELECT c.email, o.id AS order_id, o.amount_cents, o.status
FROM customers c
JOIN orders o ON o.customer_id = c.id
ORDER BY o.created_at DESC;

-- 左连接：所有客户，即使没有订单
SELECT c.email, COUNT(o.id) AS order_count, COALESCE(SUM(o.amount_cents), 0) AS total_cents
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.email
ORDER BY total_cents DESC;
```

**为什么**：关系库的价值之一就是用 JOIN 表达实体关联，而不是在应用里手工拼多表数据。  
**预期结果**：返回客户与订单的组合行，或按客户聚合的统计结果。

### 步骤 7：事务（Transaction）

事务：一组 SQL 要么全部成功提交，要么全部回滚，保证原子性。

**做什么**

```sql
BEGIN;

INSERT INTO orders (customer_id, status, amount_cents)
VALUES (1, 'paid', 1999);

UPDATE customers
SET full_name = full_name  -- 示意：可在同一事务里改多表
WHERE id = 1;

-- 确认无误
COMMIT;
-- 若中途发现错误：ROLLBACK;
```

并发下可用行锁：

```sql
BEGIN;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;  -- 锁定该行直到事务结束
UPDATE orders SET status = 'shipped' WHERE id = 1;
COMMIT;
```

**为什么**：下单扣库存、转账等必须「同成同败」；`FOR UPDATE` 防止两人同时改同一行导致丢失更新。  
**预期结果**：`COMMIT` 后数据持久；`ROLLBACK` 后像没发生过。

### 步骤 8：权限收紧（应用账号）

**做什么**

```sql
-- 示例：只给 DML，不给 DDL
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA sales TO app_user;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA sales TO app_user;

-- 对以后新建的表也自动授权（避免每次手工 GRANT）
ALTER DEFAULT PRIVILEGES IN SCHEMA sales
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
```

**为什么**：泄露应用账号密码时，攻击面更小（不能随意删库、改结构）。  
**预期结果**：用 `app_user` 能读写业务表，但不能 `DROP DATABASE`。

## 5. 完整示例：从建库到业务查询

下面给出一份可连贯执行的示例（假设你已能用超级用户进入 `psql`）。场景：极简电商订单查询。

```sql
-- ========== 1) 准备库与角色 ==========
CREATE ROLE shop_app WITH LOGIN PASSWORD 'shop_pass';
CREATE DATABASE shop OWNER shop_app;

-- 重新连接
\c shop

CREATE SCHEMA IF NOT EXISTS sales AUTHORIZATION shop_app;
SET search_path TO sales, public;

-- ========== 2) 建表 ==========
CREATE TABLE customers (
  id         BIGSERIAL PRIMARY KEY,
  email      TEXT NOT NULL UNIQUE,
  full_name  TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE products (
  id         BIGSERIAL PRIMARY KEY,
  sku        TEXT NOT NULL UNIQUE,
  title      TEXT NOT NULL,
  price_cents INTEGER NOT NULL CHECK (price_cents >= 0)
);

CREATE TABLE orders (
  id           BIGSERIAL PRIMARY KEY,
  customer_id  BIGINT NOT NULL REFERENCES customers(id),
  status       TEXT NOT NULL DEFAULT 'pending',
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id    BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id  BIGINT NOT NULL REFERENCES products(id),
  qty         INTEGER NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, product_id)
);

CREATE INDEX idx_orders_customer_id ON orders(customer_id);

-- ========== 3) 写入样例数据 ==========
INSERT INTO customers (email, full_name) VALUES
  ('alice@example.com', 'Alice'),
  ('bob@example.com', 'Bob');

INSERT INTO products (sku, title, price_cents) VALUES
  ('SKU-TEE', 'T-Shirt', 5900),
  ('SKU-MUG', 'Mug', 2900);

INSERT INTO orders (customer_id, status) VALUES (1, 'paid');

INSERT INTO order_items (order_id, product_id, qty) VALUES
  (1, 1, 2),  -- 2 件 T-Shirt
  (1, 2, 1);  -- 1 个 Mug

-- ========== 4) 业务查询：订单明细与金额 ==========
SELECT
  o.id AS order_id,
  c.email,
  p.title,
  oi.qty,
  p.price_cents,
  oi.qty * p.price_cents AS line_total_cents
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id = 1;

-- ========== 5) 授权给应用角色 ==========
GRANT USAGE ON SCHEMA sales TO shop_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA sales TO shop_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA sales TO shop_app;
```

应用侧连接串示例：

```text
postgresql://shop_app:shop_pass@localhost:5432/shop
```

在 Node.js / Python / Go 等语言中，把该 URI 交给官方或主流驱动即可（具体驱动参数以各语言文档为准）。

## 6. 常用运维

### 6.1 备份与恢复（`pg_dump` / `pg_restore`）

#### 逻辑备份单个数据库（SQL 文本）

```bash
# 备份
pg_dump -h localhost -U shop_app -d shop -F p -f shop.sql

# 恢复到空库（需先 CREATE DATABASE）
psql -h localhost -U shop_app -d shop < shop.sql
```

#### 自定义格式（便于 `pg_restore` 并行与选择性恢复）

```bash
# -F c：custom 格式
pg_dump -h localhost -U postgres -d shop -F c -f shop.dump

# 恢复
pg_restore -h localhost -U postgres -d shop --clean --if-exists shop.dump
```

#### 仅备份结构或仅备份数据

```bash
pg_dump -d shop --schema-only -f shop_schema.sql
pg_dump -d shop --data-only   -f shop_data.sql
```

**要点**：

- `pg_dump` 适合逻辑备份、迁移、较低停机要求的导出
- 超大库、时间点恢复（PITR）通常依赖 **基础备份 + WAL 归档**（进阶主题，本文仅点名）
- 备份文件要定期做「恢复演练」，否则不算真正有备份

### 6.2 配置要点

主要配置文件：

- `postgresql.conf`：运行参数
- `pg_hba.conf`：访问认证
- 数据目录位置随安装方式而变（Homebrew / apt / Docker 各不相同）**【需要确认】本机实际路径**

常用参数（概念级，调优需结合监控）：

| 参数 | 作用 |
|------|------|
| `listen_addresses` | 监听地址；生产勿随意对公网开放 |
| `port` | 端口，默认 5432 |
| `max_connections` | 最大连接数；过大浪费内存 |
| `shared_buffers` | 共享缓冲，常见起点约为内存的 25%（视负载调整） |
| `work_mem` | 单次排序/哈希操作可用内存；过大 + 高并发可能炸内存 |
| `maintenance_work_mem` | 维护操作（VACUUM/CREATE INDEX）内存 |
| `wal_level` / 归档相关 | 复制与 PITR 相关 |
| `log_min_duration_statement` | 记录慢 SQL（例如超过 500ms） |

修改后通常需要：

```bash
# 多数参数
SELECT pg_reload_conf();
# 或
# brew services restart postgresql@16
# sudo systemctl restart postgresql
```

部分参数必须重启实例才生效，改完请用文档或 `pg_settings` 确认 `context`。

### 6.3 日志

开发期建议打开慢查询与连接错误日志，便于排障：

```conf
# postgresql.conf 示意
logging_collector = on
log_destination = 'stderr'
log_min_duration_statement = 500   # 单位 ms
log_line_prefix = '%m [%p] %u@%d '
```

查看日志位置：

```sql
SHOW log_directory;
SHOW data_directory;
```

Docker 环境常用 `docker logs pg16`。

### 6.4 日常健康检查（入门）

```sql
-- 当前连接
SELECT pid, usename, datname, state, query_start, left(query, 80)
FROM pg_stat_activity
WHERE datname IS NOT NULL
ORDER BY query_start;

-- 数据库体积
SELECT pg_database.datname,
       pg_size_pretty(pg_database_size(pg_database.datname))
FROM pg_database
ORDER BY pg_database_size(pg_database.datname) DESC;

-- 表体积
SELECT relname AS table_name,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 20;
```

`VACUUM` / `ANALYZE`：回收死元组、更新统计信息，帮助优化器选对执行计划。自动 vacuum 默认开启；大表批量导入后可手动：

```sql
VACUUM (VERBOSE, ANALYZE) sales.orders;
```

## 7. 进阶概览

以下内容帮助建立「地图」，不要求一次学完。

### 7.1 视图（View）

视图是保存起来的查询，简化复杂 SQL、统一口径。

```sql
CREATE VIEW sales.v_order_totals AS
SELECT
  o.id AS order_id,
  c.email,
  SUM(oi.qty * p.price_cents) AS total_cents
FROM sales.orders o
JOIN sales.customers c ON c.id = o.customer_id
JOIN sales.order_items oi ON oi.order_id = o.id
JOIN sales.products p ON p.id = oi.product_id
GROUP BY o.id, c.email;

SELECT * FROM sales.v_order_totals;
```

物化视图（`MATERIALIZED VIEW`）会缓存结果，适合重查询；需 `REFRESH` 更新。

### 7.2 函数（Function）

把可复用逻辑放进数据库（谨慎：业务逻辑过度下沉会增加耦合）。

```sql
CREATE OR REPLACE FUNCTION sales.line_total(qty INT, price_cents INT)
RETURNS INT
LANGUAGE SQL
IMMUTABLE
AS $$
  SELECT qty * price_cents;
$$;

SELECT sales.line_total(2, 5900);
```

### 7.3 触发器（Trigger）

在表事件（INSERT/UPDATE/DELETE）前后自动执行函数，常用于审计字段、简单派生数据。

```sql
CREATE TABLE sales.audit_log (
  id         BIGSERIAL PRIMARY KEY,
  note       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE OR REPLACE FUNCTION sales.tg_log_new_order()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  INSERT INTO sales.audit_log(note)
  VALUES ('new order #' || NEW.id);
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_orders_ai
AFTER INSERT ON sales.orders
FOR EACH ROW
EXECUTE FUNCTION sales.tg_log_new_order();
```

> 不同大版本触发器语法细节可能略有差异；若报错请对照本机版本文档 **【需要确认】**。

### 7.4 JSON / JSONB

- **JSON**：文本存储，写入几乎原样保留  
- **JSONB**：二进制存储，可索引、查询通常更快（一般业务优先 JSONB）

```sql
CREATE TABLE sales.events (
  id         BIGSERIAL PRIMARY KEY,
  payload    JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

INSERT INTO sales.events (payload) VALUES
  ('{"type":"page_view","user":"alice","meta":{"path":"/home"}}');

SELECT payload->>'type' AS event_type,
       payload #>> '{meta,path}' AS path
FROM sales.events
WHERE payload @> '{"type":"page_view"}';

CREATE INDEX idx_events_payload_gin ON sales.events USING GIN (payload);
```

### 7.5 全文检索（入门）

```sql
ALTER TABLE sales.products
  ADD COLUMN title_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(title, ''))) STORED;

CREATE INDEX idx_products_title_tsv ON sales.products USING GIN (title_tsv);

SELECT sku, title
FROM sales.products
WHERE title_tsv @@ plainto_tsquery('english', 'shirt');
```

中文分词通常需要额外扩展或外部分词方案，默认英文配置对中文不理想 **【需要确认】** 业务语言方案。

### 7.6 扩展（Extension）与 PostGIS

```sql
-- 查看可用 / 已安装扩展
SELECT * FROM pg_available_extensions ORDER BY name;
\dx

-- 常用：模糊搜索、加密、UUID 等（是否可用取决于安装包是否含 contrib）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
```

**PostGIS**：在 Postgres 上提供地理空间类型、索引与函数（点线面、距离、包含关系等），是 GIS 领域事实标准之一。安装方式因 OS/镜像而异，例如：

```bash
# 概念示意：使用 PostGIS 镜像而非原版 postgres 镜像
docker pull postgis/postgis:16-3.4
```

```sql
CREATE EXTENSION IF NOT EXISTS postgis;
SELECT PostGIS_Version();
```

## 8. 常见问题与排查

### 8.1 无法连接：`connection refused`

| 项目 | 内容 |
|------|------|
| **现象** | `psql: error: connection to server at "localhost" (127.0.0.1), port 5432 failed: Connection refused` |
| **可能原因** | 服务未启动；端口不是 5432；Docker 未映射端口 |
| **解决方法** | `brew services list` / `systemctl status postgresql` / `docker ps`；确认 `-p 5432:5432`；用 `lsof -i :5432` 检查监听 |

### 8.2 认证失败：`password authentication failed`

| 项目 | 内容 |
|------|------|
| **现象** | 密码错误或认证方式不匹配 |
| **可能原因** | 密码错；连错用户；`pg_hba.conf` 要求 scram/md5 而客户端配置不对 |
| **解决方法** | 核对用户与密码；本机信任场景可临时改 `pg_hba.conf`（仅限开发）；Docker 检查 `POSTGRES_PASSWORD` |

### 8.3 `database "xxx" does not exist` / `relation does not exist`

| 项目 | 内容 |
|------|------|
| **现象** | 连错库，或表不在当前 `search_path` / Schema |
| **可能原因** | 连接串库名错误；表建在 `sales` 却查 `public` |
| **解决方法** | `\c 正确库名`；`SET search_path TO sales, public;`；用 `sales.orders` 限定 Schema |

### 8.4 权限不足：`permission denied`

| 项目 | 内容 |
|------|------|
| **现象** | 对表或 Schema 无权限 |
| **可能原因** | 未 `GRANT`；只有表权限没有 `USAGE ON SCHEMA` |
| **解决方法** | 补齐 `GRANT USAGE ON SCHEMA ...` 与表级权限；避免滥用超级用户 |

### 8.5 慢查询

| 项目 | 内容 |
|------|------|
| **现象** | 接口超时、CPU 高 |
| **可能原因** | 缺索引；统计信息过期；选了错误 JOIN 顺序；`work_mem` 过小导致落盘 |
| **解决方法** | `EXPLAIN (ANALYZE, BUFFERS) your_sql;`；给过滤/连接列建索引；`ANALYZE`；避免 `SELECT *` 大宽表 |

### 8.6 磁盘涨得快

| 项目 | 内容 |
|------|------|
| **现象** | 数据目录持续增大 |
| **可能原因** | 大量更新产生死元组；WAL 堆积；日志过多 |
| **解决方法** | 检查 autovacuum；排查长事务（会阻止清理）；检查复制槽与归档 |

## 9. 注意事项与最佳实践

### 9.1 推荐做法

1. **开发与生产隔离**：生产账号最小权限；禁止应用使用超级用户。  
2. **显式 Schema**：业务表不要全部堆在默认习惯上不加前缀；团队统一 `search_path`。  
3. **约束下沉到数据库**：`NOT NULL`、`UNIQUE`、`FOREIGN KEY`、`CHECK` 能挡住脏数据。  
4. **先有备份再做危险操作**：`DROP`/`TRUNCATE`/大变更前 `pg_dump`。  
5. **用迁移工具管 DDL**：Flyway、Liquibase、Goose、Prisma Migrate、Rails ActiveRecord 等，避免手工改生产结构。  
6. **索引不是越多越好**：加速读、拖慢写；按真实查询建。  
7. **连接池**：应用高并发时用 PgBouncer 等，避免 `max_connections` 被打满。  
8. **时间类型优先 `TIMESTAMPTZ`**：存绝对时间点，减少时区歧义。  
9. **主键**：业务主键与代理主键（`BIGSERIAL`/`IDENTITY`/`UUID`）按场景选择；分布式常见 UUID/ULID。  
10. **SQL 注入防护**：永远用参数化查询，不要拼接用户输入。

### 9.2 常见坑

| 坑 | 说明 | 规避 |
|----|------|------|
| 忘了连对数据库 | 对象建到了别的库 | 连接后先 `\conninfo` |
| `public` 一把梭 | 后期难以拆分与授权 | 按域建 Schema |
| 长事务 | 拖住 vacuum，表膨胀 | 尽快 `COMMIT`/`ROLLBACK` |
| 在循环里逐条 INSERT | 极慢 | 批量插入 / `COPY` |
| 过早微调用内存参数 | 适得其反 | 先监控，再按瓶颈调 |
| Docker 未挂卷 | 删容器丢数据 | `-v` 持久化数据目录 |
| 把 Postgres「集群」听成多机 | 概念混淆 | 分清 data cluster vs HA cluster |

### 9.3 安全底线

- 不要把数据库端口裸奔到公网
- 强密码 + 最小权限 + 必要时 SSL
- 密钥走环境变量/密钥管理，不要写入仓库
- 定期备份并演练恢复

### 10.3 备份恢复

```bash
pg_dump -d DB -F c -f db.dump
pg_restore -d DB --clean --if-exists db.dump
pg_dumpall > allroles_and_dbs.sql   # 含角色等（需足够权限）
```

### 10.4 高频 SQL

```sql
BEGIN; ... COMMIT;          -- 或 ROLLBACK;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

VACUUM (ANALYZE) table;
SHOW shared_buffers;

```

## 11. 总结与下一步

### 11.1 核心内容回顾

- PostgreSQL 是开源、强事务、可扩展的对象-关系型数据库，适合需要可靠性与复杂查询的系统。  
- 使用主线是：**安装启动 → 角色认证连接 → 库/Schema/表 → SQL 与事务 → 索引与备份**。  
- 日常开发掌握 CRUD、JOIN、事务、基础权限即可上手；视图、JSONB、触发器、扩展按需深入。  
- 运维至少做到：会 `pg_dump`/`pg_restore`、会看日志与 `pg_stat_activity`、明白配置与认证文件的职责。

### 11.2 建议的下一步

1. 用 Docker 或 Homebrew 在本机跑通第 5 章完整示例。  
2. 把示例改成你真实业务的一张主表 + 一张明细表，练习索引与 `EXPLAIN`。  
3. 写一条自动化备份脚本（每日 `pg_dump` + 保留最近 N 天）。  
4. 需要地理数据时再单独学习 PostGIS；需要海量写入时再学习 `COPY`、分区表与连接池。  
5. 以官方文档为准核对版本差异：[PostgreSQL Documentation](https://www.postgresql.org/docs/)（当前实例版本用 `SELECT version();` 确认）。
