# 域名与 DNS 使用指南（运维 / 开发实操）

## 1. 文档概述

### 解决什么问题

本指南说明**域名是什么、DNS 如何把名字解析成地址、如何购买与管理域名、如何配置常见业务记录，以及改完记录后如何验证与排障**。目标是让你能独立完成「注册域名 → 改 NS → 加记录 → 验证解析 → 对接网站/邮箱/证书」的完整闭环，并避开改 NS、删 MX、根域误用 CNAME 等会导致整站或邮件不可用的操作。

### 适合哪些读者

- 有基础网络与 Linux 命令行经验的运维、SRE、后端开发
- 需要为自己或团队的服务配置域名、子域、邮箱与 HTTPS 证书
- 需要一份可检索、可照着敲 `dig` 的实操手册（非厂商营销文）

### 阅读后能获得什么

- 理解域名层级、FQDN、与 IP 的关系，以及 DNS 递归/权威解析流程
- 认识常见记录类型（A/AAAA/CNAME/MX/TXT/NS/SOA/SRV/CAA/PTR）及适用场景
- 能按通用步骤完成选名、注册、改 NS、加记录与验证
- 能配置网站、邮箱（含 SPF/DKIM/DMARC）、所有权验证、泛域名与子域委托
- 理解 TTL/缓存与「改完要等」的原因，并按「本机 → 公网 DNS → 权威」路径排障
- 了解 HTTPS/ACME 与域名验证的关系，以及国内备案、解析差异的务实注意点

### 版本与范围说明

- 本文讲**通用域名与 DNS 机制**，不绑定某一注册商或云厂商控制台；面板名称因厂商而异，原理相同
- 命令示例以 macOS / Linux 常见的 `dig`、`nslookup`、`host` 为准；Windows 可用 `nslookup` 或安装 dig（如通过 Git Bash / WSL）
- DNS 规范以常见实践为准（RFC 体系庞大，本文不逐条引用）；个别注册商/解析商的额外限制标为 **【需要确认】**
- **不替代**：具体注册商合同条款、国内 ICP 备案办理细则、邮件服务商最新 TXT 记录模板

## 2. 前置条件

### 环境要求

| 项目 | 要求 |
|------|------|
| 本机工具 | 建议安装 `dig`（通常随 `bind-tools` / `dnsutils` / macOS 自带） |
| 权限 | 能登录域名注册商与 DNS 解析控制台 |
| 网络 | 能访问公网 DNS（如 `1.1.1.1`、`8.8.8.8`）以便对比解析结果 |
| 可选 | 已有一台公网 IP 的服务器，或 CDN / 对象存储的 CNAME 目标 |

### 必备基础知识

- 知道 IP 地址大致是什么（IPv4 / IPv6）
- 会用浏览器访问网站，知道 HTTPS 与 443 端口的基本含义
- 能区分「域名注册」和「在服务器上部署网站」是两件不同的事

### 动手前建议确认

- **【需要确认】** 域名是否已注册、注册商是谁、到期日是哪天
- **【需要确认】** DNS 托管在注册商自带解析，还是独立 DNS（Cloudflare、阿里云 DNS、自建 BIND 等）
- **【需要确认】** 业务是否需要国内备案（面向中国大陆用户的网站/App 等场景时常相关）
- **【需要确认】** 是否已有邮箱、CDN、证书自动化（ACME）等依赖域名的服务

> **核心结论先记住：** 域名本身只是可读的名字；真正让浏览器、邮件、API 找到目标的是 **DNS 记录**。改错 NS 或删错记录，影响的是「全世界怎么找到你」，往往比改错一台服务器配置更严重。

## 3. 核心概念

**先记住结论：** 域名是互联网上的层次化命名；DNS 是把域名翻译成 IP（或其他数据）的分布式数据库。你买的是「名字使用权 + 在注册局登记」，日常运维改的大多是「DNS 区里的记录」。

### 3.1 域名是什么

**域名（Domain Name）** 是一串用点分隔的标签，用来标识网络上的主机、服务或资源，例如 `www.example.com`。人记名字，机器最终靠 IP 通信；中间靠 DNS 完成映射。

与 IP 的关系：

| 概念 | 作用 |
|------|------|
| 域名 | 人类可读的标识，便于更换机房、做负载均衡、配 CDN，而不必改用户记住的入口 |
| IP | 主机在网络层的地址；一条 A/AAAA 记录把某个名字指到某个 IP |
| 一对多 / 多对一 | 一个域名可对应多个 IP（多 A 记录）；多个域名可指向同一 IP（虚拟主机） |

域名**不是**服务器上的一个文件，也**不是**自动附带网站或邮箱。注册成功后，若没有正确的 DNS 与业务侧配置，浏览器访问会失败。

### 3.2 FQDN 与层级结构

**FQDN（Fully Qualified Domain Name，完全限定域名）** 是从主机名一路写到根的完整名字，严格写法末尾带点，例如 `www.example.com.`。日常对话和多数配置里常省略末尾的点，写成 `www.example.com`。

层级从右到左（从根往下）：

```text
.                    ← 根（Root）
└── com.             ← TLD（顶级域 Top-Level Domain）
    └── example.com. ← SLD / 注册域（常说的「二级域」，你买的通常是这一层）
        └── www.example.com.     ← 子域 / 主机名
        └── api.example.com.
        └── mail.example.com.
```

常用术语：

| 术语 | 含义 | 示例 |
|------|------|------|
| 根域 | DNS 树的顶层，由根服务器管理 | `.` |
| TLD | 顶级域：通用（gTLD）如 `.com`；国家/地区（ccTLD）如 `.cn`、`.io` | `com`、`cn` |
| 注册域 / apex / zone apex | 你向注册商购买并在注册局登记的那一层 | `example.com` |
| 子域（subdomain） | 注册域之下的任意更深层标签 | `www`、`api`、`dev.ops` |
| 主机名（hostname） | 常指最左侧标签，语境依赖 | `www` |

> **注意：** 「二级域名」口语里有时指 `example.com`，有时指 `www.example.com`，容易混淆。技术讨论里优先用 **注册域 / 子域 / FQDN**。

### 3.3 DNS 是什么

**DNS（Domain Name System）** 是分布式命名系统：把查询（如「`www.example.com` 的 A 记录是什么？」）交给一串服务器，最终得到答案或「不存在」。

两类你必须分清的角色：

| 角色 | 做什么 | 典型例子 |
|------|--------|----------|
| **递归解析器（Recursive Resolver）** | 替客户端「跑腿」：查缓存；没有则从根往下问，直到拿到最终答案 | 运营商 DNS、`8.8.8.8`、`1.1.1.1`、本机 stub 转发目标 |
| **权威服务器（Authoritative Nameserver）** | 对某个区（zone）给出「官方答案」 | 你在 DNS 面板配置的 NS，如 `ns1.dns-provider.net` |

客户端（浏览器、系统）通常只问本机或局域网配置的递归解析器，**不会**自己跑完整套从根到叶的查询（除非你用 dig 指定权威）。

### 3.4 一次典型解析流程（简化）

以查询 `www.example.com` 的 A 记录为例（缓存未命中时）：

1. **客户端**向本机/运营商的**递归解析器**发起查询。
2. 递归解析器若无缓存，向**根服务器**询问：谁管 `.com`？
3. 根返回 `.com` 的 **TLD 权威** NS。
4. 递归再问 TLD：谁管 `example.com`？
5. TLD 返回 `example.com` 的 **权威 NS**（你在注册商处设置的 NS）。
6. 递归向该权威查询 `www.example.com` 的 A 记录。
7. 权威返回 IP（或 CNAME 等）；递归缓存后返回给客户端。
8. 客户端用得到的 IP 发起 TCP/TLS 连接（DNS 本身不负责传网页内容）。

```text
客户端 → 递归解析器 → 根 → TLD → 权威 NS → 答案回传（并可能被各级缓存）
```

### 3.5 常见 DNS 记录类型

| 类型 | 作用 | 典型用途 |
|------|------|----------|
| **A** | 名字 → IPv4 | 网站、API 主机 |
| **AAAA** | 名字 → IPv6 | 双栈站点 |
| **CNAME** | 名字 → 另一个名字（别名） | CDN、Paas、`www` 指到 apex |
| **MX** | 邮件交换主机与优先级 | 收信 |
| **TXT** | 任意文本 | SPF/DKIM/DMARC、所有权验证 |
| **NS** | 该区的权威名字服务器 | 委派、声明权威 |
| **SOA** | 区的权威起始信息 | 主 NS、序列号、刷新/重试/过期、负缓存 TTL 等 |
| **SRV** | 服务位置（优先级、权重、端口、目标） | 部分 VoIP、协作套件、服务发现 |
| **CAA** | 允许哪些 CA 签发证书 | 限制证书颁发机构 |
| **PTR** | IP → 名字（反向解析） | 邮件反查、部分合规场景；通常在 IP 归属方配置，不在普通域名面板 |

**CNAME 关键限制（易错）：**

- CNAME 所在名字上，**通常不能再有其他记录类型**（同名的 A、MX、TXT、NS 等冲突）。这就是「根域（apex）不宜直接挂 CNAME」的根源：apex 上必须有 SOA/NS，许多场景还有 MX/TXT。
- 部分厂商提供 **ALIAS / ANAME / 扁平化 CNAME**：在 apex 上合成 A/AAAA，属于厂商扩展，**【需要确认】** 目标 DNS 是否支持及如何配置。

### 3.6 注册商、注册局、WHOIS

| 角色 | 含义 |
|------|------|
| **注册局（Registry）** | 管理某一 TLD 的权威机构，维护该 TLD 下域名是否已被占用等 |
| **注册商（Registrar）** | 你付钱下单的零售商，代你向注册局注册/续费/过户 |
| **DNS 托管商** | 提供权威 NS 与解析面板；可以是注册商自带，也可以是 Cloudflare、云厂商 DNS、自建 |

**WHOIS**：查询域名注册信息（注册商、状态、到期日、联系人等）的机制。许多注册商提供 **WHOIS 隐私/代理**，用代理联系信息替换个人邮箱与电话，减少公开骚扰；具体是否免费、是否影响过户，以注册商说明为准（**【需要确认】**）。

### 3.7 域名生命周期（简述）

典型阶段（名称因 TLD/注册商略有差异）：

1. **可注册** → 你完成注册，进入有效期（常见 1 年起，可多年）。
2. **续费期** → 到期前续费，服务连续。
3. **宽限期（Grace Period）** → 过期后短时间内仍可按常规续费（**【需要确认】** 具体天数）。
4. **赎回期（Redemption）** → 通常需额外赎回费，价格高于普通续费。
5. **删除/重新释放** → 可能被他人注册。
6. **过户（Transfer）** → 换注册商：通常需解锁域名、获取转移码（Auth Code），并满足「注册满一定天数」等限制。

> **危险：** 域名过期未续，网站与邮箱会一起失效；赎回成本高且有时间窗。生产域名应开启自动续费，并监控到期提醒。

## 4. 实现步骤：购买与配置（通用流程）

按顺序完成下列步骤。每一步说明：**做什么 / 为什么 / 预期结果**。

### 步骤 1：选名与查重

- **做什么：** 确定注册域（如 `example.com`），在任意注册商检索是否可注册；避开商标冲突与易混淆拼写。
- **为什么：** 名字一旦用于对外品牌与证书、邮件，后期改名成本极高。
- **预期结果：** 确认目标域名可注册，或你已持有该域名。

### 步骤 2：注册并完成实名（如需要）

- **做什么：** 在注册商下单、支付、填写注册人信息；部分 TLD/地区要求实名认证。
- **为什么：** 未完成注册商要求的身份核验时，域名可能无法解析或受限。
- **预期结果：** 控制台显示域名状态正常（如 Active / ok），能看到到期日与当前 NS。

> **【需要确认】** 你所用 TLD 与注册商的实名、隐私保护、是否强制使用其 DNS。

### 步骤 3：决定 DNS 托管在哪里

两种常见模式：

| 模式 | 做法 | 适用 |
|------|------|------|
| A. 继续用注册商 DNS | 不改 NS，只在注册商解析面板加记录 | 简单站点、少折腾 |
| B. 改用第三方 / 自建权威 | 在注册商处把 NS 改成目标 DNS 提供的 NS 列表 | 需要高级功能、统一多域名、CDN 一体化等 |

### 步骤 4：修改 NS（若采用模式 B）

- **做什么：** 在**注册商**控制台把域名的 Nameserver 改为 DNS 托管商给出的主机名（通常 2～4 个，如 `ns1.example-dns.net`）。
- **为什么：** TLD 侧登记的 NS 决定「谁对该域有权威」；只在新面板加记录而不改 NS，公网仍查旧权威。
- **预期结果：** 数分钟到 48 小时内，用 dig 查 NS 已指向新值（见第 10 节）。

> **危险（整站不可达）：** 改 NS 前，请在**新 DNS 面板预先建好**至少与线上一致的关键记录（A/AAAA、MX、TXT 等）。若先改 NS、新区却是空的，全球递归会查到「无记录」，网站与邮件同时中断。改 NS 属于高风险变更，建议低峰操作并保留回滚（改回旧 NS）预案。

### 步骤 5：在 DNS 面板添加记录

- **做什么：** 按业务添加 A/AAAA/CNAME/MX/TXT 等（见第 5 节场景）。
- **为什么：** 权威区只有有记录，递归才能返回正确答案。
- **预期结果：** 面板列表可见记录；向权威 NS 查询能返回预期值。

### 步骤 6：验证解析

- **做什么：** 用 `dig` 分别查递归与权威；浏览器或 `curl` 测 HTTP；邮箱用外部 MX 检测工具或发测试信。
- **为什么：** 控制台显示「已保存」≠ 全球递归已更新；验证要分层。
- **预期结果：** 权威已正确；常用公共 DNS 已一致或在 TTL 内可解释的滞后；业务侧连通。

### 步骤 7：配置业务与证书

- **做什么：** Web 服务器/CDN 绑定主机名；申请 TLS 证书；邮箱按服务商要求加 MX/TXT。
- **为什么：** DNS 只解决「找到谁」；HTTPS、虚拟主机、邮件路由还需业务配置。
- **预期结果：** `https://你的域名` 证书匹配；邮件可收发（若需要）。

## 5. 完整示例与常见使用场景

以下示例域名一律用 `example.com`，IP 与目标主机名为占位符，请替换为你的真实值。

### 5.1 网站：A / CNAME + 可选 CDN

**无 CDN、源站直出：**

| 主机记录 | 类型 | 值 | 说明 |
|----------|------|-----|------|
| `@` 或留空（apex） | A | `203.0.113.10` | 根域 `example.com` |
| `www` | A | `203.0.113.10` | 或 CNAME 到 `example.com`（注意部分面板语法） |

**使用 CDN（常见）：**

| 主机记录 | 类型 | 值 |
|----------|------|-----|
| `www` | CNAME | `www.example.com.cdn-provider.net`（以 CDN 控制台为准） |
| `@` | A / ALIAS / 按 CDN 要求 | apex 常需 A 记录或厂商 ALIAS，**不能**随意对 apex 做标准 CNAME |

操作要点：

1. 在 CDN 添加加速域名并完成归属验证（常为 TXT 或代持 CNAME）。
2. 按 CDN 文档改 DNS。
3. 源站仍需配置正确的 Host / 回源与证书（**【需要确认】** CDN 与源站证书策略）。

### 5.2 邮箱：MX + SPF / DKIM / DMARC

邮件依赖 **MX** 指向邮件服务器；反垃圾依赖若干 **TXT**：

| 记录 | 作用 |
|------|------|
| MX | 告诉发送方「信送到哪台主机」；数字越小优先级越高（同优先级看实现） |
| SPF（TXT） | 声明哪些 IP/机制被允许以该域发信 |
| DKIM（TXT） | 公钥，供收信方验证签名 |
| DMARC（TXT） | 基于 SPF/DKIM 对齐结果的策略（`none` / `quarantine` / `reject`） |

示例（值仅为示意，**务必复制邮件服务商提供的最终字符串**）：

```text
; MX
example.com.   MX 10 mail.provider.example.

; SPF
example.com.   TXT "v=spf1 include:_spf.provider.example ~all"

; DKIM（主机名由服务商指定）
selector._domainkey.example.com.  TXT "v=DKIM1; k=rsa; p=MIGfMA0GCS..."

; DMARC
_dmarc.example.com.  TXT "v=DMARC1; p=none; rua=mailto:dmarc-reports@example.com"
```

> **危险：** 删除或改错 **MX**，会导致该域收信失败（发信方找不到正确邮件服务器）。更换邮箱服务商时，应先加齐新 MX/TXT，验证后再删旧 MX，并预留 TTL 与双轨过渡时间。

> **危险：** 多个互斥的 SPF 挤在多条 TXT 里、或 SPF 机制过多导致查询链过长，都会让反垃圾判定异常。保持**一条**合并好的 SPF（按服务商文档）。

### 5.3 验证域名所有权（TXT）

云厂商、CDN、搜索站长、证书服务等常要求你在 DNS 添加指定 TXT（或特定前缀主机名）：

```text
_acme-challenge.example.com.  TXT "随机令牌"
# 或
example.com.  TXT "vendor-verification=abcdef"
```

**做什么：** 原样添加 → 等权威生效 → 在厂商控制台点验证。  
**预期结果：** 厂商查询到完全一致的字符串。注意区分「加在根域」还是「加在 `_acme-challenge` 等子名」。

### 5.4 泛域名 `*.example.com`

| 主机记录 | 类型 | 值 | 效果 |
|----------|------|-----|------|
| `*` | A | `203.0.113.10` | `任意.example.com`（单层）指向该 IP |

要点：

- 泛域名通常只匹配**一层**标签：`*.example.com` 匹配 `foo.example.com`，**不匹配** `a.b.example.com`（需 `*.b.example.com` 或更具体记录）。
- 更具体的记录优先于通配符。
- TLS 需要**泛域名证书**（如 `*.example.com`）或自动化为每个主机名签证书；仅有泛 DNS **不会**自动有 HTTPS。

### 5.5 从零配置一个最小可用站（串联示例）

假设：域名 `example.com` 已注册；服务器 IPv4 为 `203.0.113.10`；继续用注册商 DNS。

1. 在解析面板添加：
   - `@` → A → `203.0.113.10`（TTL 300 便于初次调试，稳定后调大）
   - `www` → A → `203.0.113.10`（或 CNAME → `example.com`）
2. 服务器 Nginx/Caddy 配置 `server_name example.com www.example.com;` 并监听 80/443。
3. 用 ACME 申请证书（HTTP-01 或 DNS-01，见第 8 节）。
4. 验证：

```bash
dig +short example.com A
dig +short www.example.com A
curl -I http://example.com
```

**预期结果：** dig 返回 `203.0.113.10`；HTTP 有响应；证书签发后 HTTPS 正常。

## 6. 子域与分区（Zone）实践

### 6.1 子域划分实践

常见划分方式：

| 子域 | 用途 |
|------|------|
| `www` | 主站 |
| `api` / `app` | API 或应用入口 |
| `staging` / `dev` | 非生产环境（注意不要暴露敏感系统） |
| `mail` / `smtp` | 邮件相关主机名（MX 目标常是服务商主机名） |
| `cdn` / 静态资源域 | 与主站 cookie 隔离等 |

原则：按环境与团队边界划分，避免所有服务挤在少量主机名上难以做证书与权限隔离；也不要过度碎片化导致记录失控。

### 6.2 委托（NS 委派）概念

**委派（Delegation）**：在父区用 **NS 记录**（及必要的 glue A/AAAA）声明「某个子域的权威是另一组 NS」。

示例：把 `ops.example.com` 整棵子树交给另一套 DNS：

```text
; 在 example.com 区中：
ops.example.com.     NS  ns1.ops-dns.example.
ops.example.com.     NS  ns2.ops-dns.example.
; 若 ns1 本身在 ops.example.com 下，还需 glue A/AAAA（由 DNS 服务商协助配置）
```

- **做什么：** 父区加子域 NS；子域权威上配置完整 zone（含 SOA）。
- **为什么：** 大组织或多云场景下，让子域团队独立管理解析。
- **预期结果：** 查 `api.ops.example.com` 时，递归会跟随委派到子域权威。

> **易错：** 只在子域 DNS 面板加了记录，但父域从未委派 NS → 公网查不到。或委派了但子域权威无 SOA/无记录 → 解析失败。

## 7. TTL、缓存与生效时间

### 7.1 TTL 是什么

**TTL（Time To Live）** 是权威在应答里声明的「这条答案可以被缓存多久（秒）」。递归解析器（以及部分系统/浏览器侧行为）会在 TTL 内直接返回缓存，不必每次问权威。

### 7.2 为什么「改完要等」

1. 你改的是**权威**上的数据，权威侧通常很快一致（主备同步另说）。
2. 全球无数递归解析器里，可能仍缓存着**旧答案**，直到各自缓存的 TTL 到期。
3. 本机 OS、浏览器、公司内网 DNS、运营商 DNS 都可能再缓存一层。
4. 因此：「我这边 dig 已经是新 IP，同事仍是旧 IP」完全正常，多半是缓存差异。

### 7.3 变更策略建议

| 场景 | 建议 |
|------|------|
| 即将切 IP / 切 CDN | 提前把相关记录 TTL 降到 300（或服务商允许的最小值），等旧 TTL 过完再切 |
| 稳定运行 | TTL 用 3600～86400 等较常见值，减少查询量与偶发抖动 |
| 刚改完验证 | **直接查权威 NS**，不要只查本机默认 DNS |

> **注意：** 长期把全部记录 TTL 设为 60 秒，会增加权威与递归压力，且对「秒级切换」帮助有限（客户端与中间缓存行为仍不可控）。切流窗口过后再调高 TTL。

### 7.4 负缓存

查询不存在的名字时，权威通过 SOA 中的 MINIMUM 等字段影响**否定答案**的缓存时间。刚删记录或拼写错误时，「没有记录」也可能被缓存一段时间，排障时同样要分层验证。

## 8. HTTPS 与域名（简述）

**TLS 证书**证明「持有某私钥的一方被 CA 认可控制某些域名」。浏览器用证书里的名字（SAN）与你在地址栏访问的主机名比对。

**ACME**（如 Let’s Encrypt 使用的协议）常见域名验证方式：

| 方式 | 做法 | 依赖 |
|------|------|------|
| HTTP-01 | 在 `http://域名/.well-known/acme-challenge/...` 放令牌 | 域名 A/AAAA 已指向可应答的 80 端口 |
| DNS-01 | 在 `_acme-challenge.域名` 放 TXT | 能写 DNS；适合泛域名证书、或 80 端口不可达 |
| TLS-ALPN-01 | 在 443 上按约定应答 | 较少用于入门场景 |

关系小结：

- 证书绑定的是**域名**，不是 IP（虽有少数 IP 证书，非本文重点）。
- DNS 未指向正确主机时，HTTP-01 会失败。
- 仅配好 DNS 而无证书，用户访问 HTTPS 会报错；仅有证书而 DNS 指错，会连到错误主机。
- **CAA 记录**可限制允许签发的 CA；配错可能导致合法续期失败，改 CAA 前确认自动化续期使用的 CA。

## 9. 国内常见注意（务实）

### 9.1 备案（概念与何时相关）

**ICP 备案**是中国大陆对部分互联网信息服务的管理要求。实务上：

- 若网站**托管在中国大陆境内的服务器**并向公众提供服务，接入云厂商时通常会被要求完成备案，并可能校验域名与主体信息。
- 若源站仅在海外、或仅内部使用等，是否需要备案取决于具体业务与接入方式——以云厂商/接入商当期审核要求为准（**【需要确认】**），本文不展开政策条文。
- 备案与「域名能否在注册商注册」不是同一件事；也与 DNS 是否能解析不是同一件事。

### 9.2 解析差异与「污染」排查思路

现象：同一域名，在不同网络、不同 DNS 上结果不一致，或国内/海外访问异常。

务实排查顺序：

1. **确认权威答案**：`dig @权威NS 域名 A`，这是「你配置的真相」。
2. **对比公共递归**：`dig @8.8.8.8`、`dig @1.1.1.1`、以及当前网络默认 DNS。
3. **区分缓存与篡改**：若权威正确、个别递归长期错误且远超 TTL，再考虑运营商劫持、错误的本地 hosts、公司 DNS 策略、或恶意软件改配置等。
4. **区分 DNS 与线路**：DNS 已正确但网页打不开，可能是跨境网络、防火墙、源站安全组、HTTP 服务本身问题——用 `curl -v`、换网络、测 IP 直连（注意虚拟主机需带 Host）分开验证。
5. **DoH/DoT**：部分客户端绕过系统 DNS，会导致「系统 dig 与浏览器不一致」。

不要一上来假设「被污染」；多数事故是 NS 改错、记录未加、TTL 缓存、hosts 残留或只改了面板未改注册商 NS。

## 10. 常见问题与排查

### 10.1 排障总路径（推荐固定顺序）

```text
1) 本机 hosts / 本机缓存
2) 本机默认递归（运营商或公司 DNS）
3) 公共递归（1.1.1.1 / 8.8.8.8）
4) 域名权威 NS（dig NS → dig @ns ...）
5) 业务层（安全组、Web、证书、CDN 回源）
```

### 10.2 常用命令

```bash
# 查 A
dig example.com A +short

# 查详细过程（含权威标记）
dig example.com A +noall +answer +authority +additional

# 指定公共 DNS
dig @1.1.1.1 www.example.com A
dig @8.8.8.8 www.example.com A

# 先查 NS，再问权威
dig example.com NS +short
dig @ns1.你的权威.net example.com A

# MX / TXT / CNAME
dig example.com MX
dig example.com TXT
dig www.example.com CNAME

# 追踪委派（从根或中间）
dig +trace example.com A

# 其他工具
nslookup example.com
nslookup example.com 8.8.8.8
host example.com
host -t MX example.com
```

### 10.3 现象 → 原因 → 处理

| 现象 | 可能原因 | 解决方法 |
|------|----------|----------|
| 浏览器无法解析域名 | 无 A/AAAA/CNAME；NS 错误；域名过期 | 查权威；检查注册商域名状态与 NS |
| 我这边正常同事不行 | 递归缓存未过期；不同 DNS | 对比 dig；等待 TTL；清本地 DNS 缓存 |
| 改了记录没变化 | 改错区/错主机名；只改了未生效的 DNS 面板；TTL | 确认当前权威 NS；`dig @权威` |
| 只有 www 能开根域不能 | apex 无 A/ALIAS；只配了 www | 为 `@` 补记录或按 CDN 要求配置 apex |
| 邮件收不到 | MX 缺失/错误；域名过期；邮件商侧拒绝 | `dig MX`；查邮件商状态；勿在切换中途删光 MX |
| 证书申请失败 | DNS 未指到本机；TXT 未生效；CAA 阻止 | 检查 HTTP-01 可达性或 DNS-01 TXT；查 CAA |
| 改 NS 后全球不通 | 新区记录未迁移完整 | 立即在新区补齐记录或回滚 NS |

### 10.4 清理本机 DNS 缓存（示例）

```bash
# macOS（系统版本不同命令可能略有差异）
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# systemd-resolved（部分 Linux）
sudo resolvectl flush-caches
```

> **【需要确认】** 你当前 OS 的确切清缓存命令；清缓存不能强制刷新运营商递归上的缓存。

## 11. 注意事项与最佳实践

### 11.1 高危操作清单（醒目）

| 操作 | 风险 | 缓解 |
|------|------|------|
| 修改 NS | 整站、邮箱、所有子域解析可能中断 | 新区预建记录 → 再改 NS；保留回滚 |
| 删除/改错 MX | 收信失败 | 变更窗口、双 MX 过渡、先加后删 |
| 根域使用标准 CNAME | 与 SOA/NS/MX/TXT 冲突，部分场景直接被拒 | 用 A/AAAA 或厂商 ALIAS/ANAME |
| 域名过期 | 全部依赖域名的服务失效，甚至被抢注 | 自动续费 + 监控到期 + 多联系人 |
| 误删 TXT（SPF/验证） | 邮件进垃圾箱或厂商验证失败 | 变更审计；重要 TXT 变更走评审 |
| TTL 长期极短 | 解析流量大、故障面更「即时」但未必更稳 | 仅在切流窗口降 TTL |

### 11.2 推荐实践

1. **权威与递归分开验证**：上线检查清单里固定包含 `dig @权威NS`。
2. **关键记录冗余**：NS 至少 2 个且分属合理网络；MX 可按服务商建议配主备；多 A 记录做简单冗余时注意应用会话与健康检查。
3. **少用过短 TTL 长期运行**：稳定期用小时级；变更前再降低。
4. **CNAME 平坦化注意**：CNAME 链过长增加失败点与延迟；CDN/厂商若提供「一次解析到位」的方式，优先按文档配置。
5. **根域（apex）策略**：优先 A/AAAA 或多线解析；确需 CNAME 语义时用支持 ALIAS 的 DNS。
6. **文档化**：把注册商账号、DNS 托管位置、到期日、NS 列表、证书自动化方式记在团队 runbook。
7. **权限与 MFA**：注册商与 DNS 控制台开启 MFA，防止域名劫持（改 NS 是经典攻击路径）。
8. **CAA + 监控**：生产域可配 CAA，并对解析与证书过期做监控。

### 11.3 选型小记

| 方案 | 适用 | 限制 |
|------|------|------|
| 注册商自带 DNS | 个人站、记录少 | 高级功能、API、全局流量管理可能弱 |
| 云厂商 DNS | 已与云资源集成 | 注意跨云、锁定效应 |
| CDN 一体化 DNS | 强依赖该 CDN | 迁出成本；apex 规则看厂商 |
| 自建权威（BIND/PowerDNS 等） | 强可控、特殊委派 | 运维与安全责任自担，需高可用 |

## 12. 总结

- **域名**是层次化名字；**DNS**把名字解析成 IP 或其他数据；你买的是注册域，日常改的是权威区里的记录。
- 分清 **注册商（买卖/NS 登记）** 与 **DNS 托管（权威记录）**；改 NS 前必须先在新区备好记录。
- 网站靠 A/AAAA/CNAME；邮件靠 MX + SPF/DKIM/DMARC；验证与 ACME 常用 TXT；泛域名解决「多子域同一目标」，证书需单独规划。
- **TTL** 解释「为什么要等」；排障固定走「本机 → 公共递归 → 权威 → 业务」。
- 最贵的错误往往是：改 NS 未迁移记录、删 MX、域名过期、apex 乱挂 CNAME。

### 下一步建议

1. 列出你名下每个生产域名的：注册商、到期日、当前 NS、DNS 面板入口。
2. 对主站执行一次 `dig +trace` 与 `dig @权威`，确认与面板一致。
3. 若近期要切流，提前降低 TTL，并写回滚步骤（含 NS 与记录）。
4. 为邮箱与证书续期分别做一次演练（测试 TXT/MX 变更与 ACME 续期）。
