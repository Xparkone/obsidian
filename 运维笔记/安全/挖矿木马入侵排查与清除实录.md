## 二、发现过程：从一个 Vim 报错开始

### 2.1 现象

以 **root** 身份编辑 `~/.ssh/authorized_keys`（权限 `-rw------- root root`，完全正常）保存时报：

```
E45: 'readonly' option is set (add ! to override)
```

root 不受权限位限制，权限正常却报只读——说明原因不在 `chmod` 这一层。

### 2.2 E45 只读报错排查顺序（通用速查）

```bash
ls -l <file>                 # 1. 权限位与属主（root 可跳过）
mount | grep ' / '           # 2. 文件系统是否只读(ro)挂载
lsattr <file>                # 3. 扩展属性 i(immutable) / a(append-only) —— root 也受限，常被忽略
```

本次结论：`mount` 正常(rw)，但 `lsattr` 显示：

```
----ia--------e------- /root/.ssh/authorized_keys
```

- `i`（immutable）：任何人（含 root）不可修改/删除/重命名；
- `a`（append-only）：只能追加；
- `e` 是 ext4 默认属性（extents），正常。

**`authorized_keys` 被锁 `+ia`，在运维里几乎没有正当理由——这是典型的入侵后门持久化手法：攻击者写入自己的公钥后锁死文件，让管理员删不掉。**

解锁方法：

```bash
chattr -ia <file>
```

## 五、根因分析（为什么会被攻破）

1. **sshd 配置过松**：`PermitRootLogin yes` + 口令认证未关闭 → root 可被密码直接登录/暴破；
2. **全员 NOPASSWD sudo**：`/etc/sudoers.d/` 下 6 个账号全部 `NOPASSWD:ALL`——任何一个账号弱口令/私钥泄露，一步即可提权 root；
3. **K8s 内网横向环境**：此类 SSH 蠕虫打下一个节点后会顺着内网（10.0.x）暴破全部相邻节点，通常不止一台中招；
4. 木马配合："后门 key 铺满所有账号 + 锁文件 + 双保活（cron+systemd）+ 清历史记录"，工程化的持久化组合拳。

## 六、应急处置（顺序敏感：先掐保活，再杀进程）

```bash
# 0. 取证备份
mkdir -p /root/evidence
cp -a /var/tmp/48937860 /var/tmp/.ladyg0g0 /usr/bin/ssshd \
  /lib/systemd/system/myservices.service /root/evidence/ 2>/dev/null
crontab -l > /root/evidence/root.crontab.bak

# 1. 掐断 crontab 保活（root 的 4 行全是恶意行 → 直接清空；有正常任务则手动删）
crontab -r && crontab -l

# 2. 掐断 systemd 保活
systemctl stop myservices.service
systemctl disable myservices.service
rm -f /etc/systemd/system/multi-user.target.wants/myservices.service \
      /lib/systemd/system/myservices.service /usr/lib/systemd/system/myservices.service \
      /usr/bin/ssshd
systemctl daemon-reload

# 3. 杀进程（先 watchdog 11810e4d，后矿工主程序；PID 会变，用模式匹配兜底）
pkill -9 -f '/var/tmp/[0-9a-f]*\./'
ps aux | grep -E '7c4884a2|11810e4d' | grep -v grep   # 应为空

# 4. 删落地文件
rm -rf /var/tmp/48937860 /var/tmp/7887faa3 /var/tmp/.ladyg0g0

# 5. 拔后门：所有账号删除攻击者公钥（被锁的先 chattr -ia，含 .ssh 目录）
chattr -ia /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys /home/*/.ssh 2>/dev/null
sed -i '/ElPatrono1337/d' /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys
grep -rl 'ElPatrono1337' /root/.ssh /home/*/.ssh 2>/dev/null   # 无输出=清干净

# 6. 跨过一个 cron 周期后验证不复发
sleep 90
uptime                                                  # load 应明显下降
ps aux | grep -E '7c4884a2|11810e4d' | grep -v grep
ls /var/tmp/.ladyg0g0 2>&1                              # 应 No such file
crontab -l                                              # 应仍为空
lsattr /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys | awk '$1 ~ /i|a/ {print "被锁:", $2}'
tail -20 /var/log/auth.log | grep 'Failed password'     # 暴破声应停止
```

任何一项"复活"都说明还有未挖出的持久化点——停止手工排查，直接下线重装。

## 七、踩坑记录（本次的两个教训）

### 7.1 `sed -i` 报 `cannot rename ... Operation not permitted`

root 执行 `sed -i` 仍被拒，原因是 **`/home/*/authorized_keys` 也被木马拉了 `+i/+a` 锁**（sed -i 采用"写临时文件再 rename"实现，immutable 文件/目录会让 rename 失败）。先 `chattr -ia`（包括 `.ssh` 目录本身）再 sed。排查时举一反三：**木马对 root 做的事，大概率对全账号都做了**。

### 7.2 `lsattr file | grep -E 'i|a'` 永远误报

正则匹配的是整行文本，文件名 `authorized_keys` 本身含字母 `i`/`a`，必然命中。只看属性字段：

```bash
lsattr <file> | awk '$1 ~ /i|a/'
```

## 八、后续加固与经验总结

### 8.1 失陷机器的处置原则

- root 失陷过的机器，手工清理只是止血；**正确做法是 cordon/drain 摘节点 → 重装系统**：
  ```bash
  kubectl cordon <node> && kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
  ```
- 攻击者拿过 root，没人能穷举所有后门藏点（还可能有 ld.so.preload、内核模块、计划任务变种等）。

### 8.2 止血后当天必须做的加固

```bash
# /etc/ssh/sshd_config
PermitRootLogin prohibit-password      # 或 no
PasswordAuthentication no
```

- 收回/收敛 `/etc/sudoers.d/` 下的 `NOPASSWD:ALL`（按需授权，标注负责人）；
- 全部账号轮换密码与密钥对；`chattr +i` 保护不了文件（攻击者拿了 root 自己就能锁），**别用锁文件当防护**；
- 失陷排查完成前，不要从该机向公网建反向隧道暴露 22 端口。

### 8.3 集群横向扫描（同网段每台都跑）

```bash
grep -rl 'ElPatrono1337' /root/.ssh /home/*/.ssh 2>/dev/null
lsattr /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys 2>/dev/null | awk '$1 ~ /i|a/'
crontab -l 2>/dev/null | grep -E 'var/tmp|disown'
ls -d /var/tmp/.ladyg0g0 /var/tmp/[0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f] 2>/dev/null
ls /lib/systemd/system/myservices.service /usr/bin/ssshd 2>/dev/null
ps aux --sort=-%cpu | head -5     # 异常高 CPU 的随机名进程
```

### 8.4 检测信号总结（下次同类事件直接套）

1. 权限正常却报只读/Operation not permitted → `lsattr` 查 `+i/+a`；
2. `authorized_keys` 出现不认识的 key（尤其 PuTTY 风格注释）出现在**多个账号同一位置** → 按失陷处理；
3. 负载异常高 + 随机十六进制进程名 → 矿工实锤；
4. `last`/`bash_history` 异常干净 ≠ 安全，恰是反取证信号；
5. crontab 里 `> /dev/null 2>&1 & disown` 组合 → 恶意保活特征。

